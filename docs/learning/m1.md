## 1. Vòng đời process & event loop

### Câu hỏi

`main()` trong [`src/index.ts`](../../src/index.ts) chạy hết trong vài ms. Không `await`, không `while(true)`.
Lẽ ra process phải thoát. Nhưng nó sống mãi. Vì sao?

### Nguyên lý

> **Node không thoát khi "hết code". Node thoát khi libuv không còn `ref`'d handle hoặc request nào.**

`new WebSocket(url)` mở một TCP socket → libuv tạo handle và đánh dấu `ref`.
Sau mỗi vòng lặp, event loop hỏi "còn handle `ref` nào không?" → còn → quay tiếp.

Đây là quy tắc gốc, giải thích luôn cả cảnh báo ở cuối [`architecture.md`](../architecture.md):
khi socket đóng mà M1 chưa reconnect, handle cuối cùng biến mất → **Node thoát lặng lẽ**.
`process.on("SIGINT", …)` _không_ giữ event loop sống — listener không phải handle.

### Thí nghiệm 1 — nhìn thấy thứ đang giữ process

Thêm tạm vào `index.ts` sau `priceService.start()`:

```ts
setInterval(() => {
    logger.info({ resources: process.getActiveResourcesInfo() }, "alive because");
}, 5000).unref();
```

Sẽ thấy `TCPSocketWrap`, `TTYWrap`…

`.unref()` ở cuối không phải chi tiết phụ: nó nói với libuv _"handle này không được tính là lý do giữ process sống"_.
Bỏ `.unref()` đi thì chính cái timer debug này cũng giữ process sống mãi.

### Thí nghiệm 2 — chứng minh ngược

Trong `binancePriceService.ts`, ngay sau `this.socket = socket`:

```ts
// @ts-expect-error — thí nghiệm, xoá sau khi thử
socket._socket?.unref();
```

Process **thoát ngay** dù socket vẫn đang kết nối và dữ liệu vẫn đang về.
Bằng chứng trực tiếp: cái giữ process sống là _handle được ref_, không phải "có việc đang làm".

### 6 phase của event loop

```
   ┌──►  timers        setTimeout / setInterval đến hạn
   │     pending       callback lỗi hệ thống bị hoãn (VD: TCP ECONNREFUSED)
   │     idle, prepare nội bộ libuv
   │     poll     ★    ĐỌC I/O — frame Binance rơi vào ĐÂY
   │     check         setImmediate
   └───  close         socket.on("close")
```

Hai hệ quả đọc thẳng từ sơ đồ:

- Handler `message` chạy ở **poll**.
- Handler `close` chạy ở **close phase** — luôn sau, không bao giờ chen ngang giữa các message.

Giữa **mỗi** callback, Node xả sạch hai hàng đợi microtask, theo thứ tự:
`process.nextTick` queue **trước**, rồi Promise queue.

### Thí nghiệm 3 — thứ tự thực thi

Thay tạm handler `message`:

```ts
socket.on("message", () => {
    console.log("1 — sync, trong poll phase");
    setTimeout(() => console.log("5 — timers, VÒNG SAU"), 0);
    setImmediate(() => console.log("4 — check, cùng vòng"));
    Promise.resolve().then(() => console.log("3 — microtask"));
    process.nextTick(() => console.log("2 — nextTick, ưu tiên cao nhất"));
});
```

Luôn ra `1 → 2 → 3 → 4 → 5`.

`4` trước `5` vì: đang ở **poll**, `check` là phase kế tiếp ngay; `timers` phải chờ hết vòng.

> `setTimeout(fn, 0)` **không** phải "chạy ngay". Nó là _"sớm nhất có thể ở phase timers của vòng sau"_.
> Một callback block 200ms sẽ làm timer 0ms của bạn trễ 200ms.

## 2. Buffer & WebSocket framing

### Vì sao `data` là `Buffer`, không phải `string`

Binance gửi JSON — text. Nhưng mạng không biết "text", mạng chỉ có **bytes**.

WebSocket có hai loại frame (text opcode `0x1`, binary `0x2`), nhưng `ws@8` mặc định giao **Buffer cho cả hai**,
kèm một cờ phân biệt:

```ts
socket.on("message", (data: RawData, isBinary: boolean) => {});
```

Code M1 bỏ qua tham số thứ hai — chấp nhận được vì Binance chỉ gửi text frame.

`Buffer` là subclass của `Uint8Array`, nhưng bộ nhớ nằm **ngoài V8 heap** (external memory).
Đó là lý do một app Node stream nhiều dữ liệu có thể ngốn RAM trong khi `heapUsed` vẫn nhỏ —
phải nhìn `external` trong `process.memoryUsage()`.

### Chuỗi biến đổi mỗi tick

```
bytes trên dây             →  Buffer (off-heap)          raw
  .toString()              →  string UTF-8 (V8 heap)     copy #1
  JSON.parse()             →  object (V8 heap)           copy #2
  { symbol, price, ts }    →  PriceTick                  copy #3
```

**Ba lần cấp phát cho mỗi tick.** BTC+ETH ~20–50 tick/giây → hàng trăm object rác mỗi giây.
V8 gom rác lớp trẻ (scavenger) rất nhanh nên ở quy mô này hoàn toàn ổn — nhưng đây chính là lý do
hệ thống tần suất cao thật sẽ parse **trực tiếp trên Buffer**, không đi qua string.

### Thí nghiệm 4 — nhìn bytes thật

```ts
socket.on("message", (data: Buffer) => {
    logger.info(
        {
            isBuffer: Buffer.isBuffer(data),
            bytes: data.length,
            firstBytes: [...data.subarray(0, 12)], // mã ASCII
            preview: data.subarray(0, 40).toString(),
        },
        "raw frame",
    );
});
```

`firstBytes` bắt đầu bằng `123` = `{`. Bytes là bytes.

### Framing — thứ `ws` cho bạn miễn phí

Với TCP thuần, bạn phải tự xử lý: một message bị chẻ làm 3 gói, hoặc 5 message dính vào một gói.
Tự tìm ranh giới là việc của bạn.

WebSocket có **length prefix trong frame header**, và `ws` đã ráp lại giúp:

> **Cam kết: một lần `message` = đúng một message hoàn chỉnh.** Không bao giờ nửa cái JSON.

`ws` cũng lo giúp: ghép continuation frame, tự trả `pong` khi server `ping` (giữ kết nối sống),
và giải nén nếu hai bên thương lượng `permessage-deflate`. Bạn nhận sản phẩm đã sạch.

## 3. EventEmitter — và cái bẫy lớn nhất của cả project

### `emit()` là ĐỒNG BỘ

Hiểu lầm phổ biến nhất. Chữ "event" gợi ý bất đồng bộ. Nó **không**.

`this.emit("tick", tick)` gọi listener **ngay lập tức, trên cùng call stack**.
Không hàng đợi, không `setImmediate`. Bản chất `emit` chỉ là:

```ts
emit(event, ...args) {
    for (const listener of this._events[event]) listener(...args);
    return listeners.length > 0;
}
```

**Thí nghiệm 5** — chèn `console.log` quanh `emit` và trong listener, sẽ ra `trước emit → trong listener → sau emit`.
Nếu async thì phải là `trước → sau → trong`.

### Hệ quả 1 — listener chậm chặn ingest

Chèn thử vào listener trong `index.ts`:

```ts
priceService.on("tick", (tick) => {
    const until = Date.now() + 500;
    while (Date.now() < until) {} // block 500ms
    logger.info(tick, "tick");
});
```

Chạy `npm run dev`. Tick tuôn ra theo **cụm giật cục**, không còn đều.
Trong 500ms đó event loop đứng hình ở poll phase: không đọc socket, không chạy timer, không làm gì cả.
Frame dồn trong TCP receive buffer của kernel.

> ### Đây là bài học trung tâm của cả project
> Ingest và delivery dính liền ⇒ một cái chậm thì **cả hai** chết.
> M4 chèn queue vào giữa chính là để cắt sợi dây này.

### Hệ quả 2 — EventEmitter KHÔNG có backpressure

| | EventEmitter | Stream |
|---|---|---|
| Mô hình | push | push + pull |
| Nói được "chậm lại"? | **Không** | Có (`write()` trả `false`, `pause()`) |
| Consumer chậm thì | Block, hoặc phình RAM | Producer tự dừng |

`emit` không có đường phản hồi — producer không thể biết consumer có theo kịp không.
Hai lối thoát, cả hai đều tệ:

- Listener **đồng bộ** → block ingest (thí nghiệm trên)
- Listener **async fire-and-forget** → RAM phình vô hạn nếu Discord chậm hơn Binance

Lối thứ ba mới đúng: **bounded queue** có chính sách drop rõ ràng.
Đó là `QUEUE_MAX` đã nằm sẵn trong [`src/config/env.ts`](../../src/config/env.ts), chờ M4.

### Hệ quả 3 — listener throw sẽ giết process

Không có `try/catch` nào bọc quanh `emit`. Exception leo ngược:

```
listener → emit() → handler "message" → callback libuv → uncaughtException → chết
```

M2 sẽ bắt `uncaughtException` / `unhandledRejection` chính vì đường leo này.

### Event `error` là trường hợp đặc biệt

Quy tắc riêng của EventEmitter:

> **`emit("error")` mà không có listener `"error"` nào sẽ THROW**, chứ không bị bỏ qua im lặng.

Nên dòng này trong `binancePriceService.ts` không phải cho đẹp — nó là thứ ngăn process chết mỗi lần mạng chập:

```ts
socket.on("error", (err) => logger.error({ err }, "Binance WS error"));
```

Xoá đi rồi rút mạng, process sẽ crash.

### Bẫy đang chờ ở M2

`stop()` gọi `close()` rồi gán `this.socket = null`, nhưng **không gỡ listener**.

M1 chỉ chạy một lần nên vô hại. M2 reconnect sẽ gọi `start()` lặp lại — mỗi socket cũ vẫn giữ 4 listener
và bị closure tham chiếu → rò rỉ dần. Sẽ cần `socket.removeAllListeners()`.

Liên quan: EventEmitter cảnh báo `MaxListenersExceededWarning` khi vượt 10 listener cùng loại trên một emitter.
Đó là **bộ dò rò rỉ bộ nhớ có chủ đích** của Node, không phải giới hạn kỹ thuật.
Thấy nó = bạn đang đăng ký lặp mà quên gỡ.

## 4. Trust boundary — biên giới dữ liệu ngoài / dữ liệu của tôi

### Nguyên lý

> Mọi thứ vào từ ngoài process đều là **`unknown`**, không phải kiểu bạn mong đợi.

Binance có thể đổi schema, gửi control frame, hoặc bạn kết nối nhầm endpoint.
TypeScript **không** bảo vệ ở đây — nó biến mất lúc runtime.

[`binanceMessage.ts`](../../src/ingest/binanceMessage.ts) khai báo đúng tinh thần đó (`let parsed: unknown`),
rồi thu hẹp dần bằng **type predicate**:

```ts
function isTradeMessage(value: unknown): value is BinanceTradeMessage;
```

`value is X` là một **lời hứa** với compiler: _"nếu tôi trả `true`, hãy tin đây là `X`"_.
Compiler **không kiểm chứng** lời hứa này — hứa sai thì nó tin sai.
Type guard vì thế là chỗ phải cẩn thận nhất trong toàn bộ codebase.

### Vì sao `null` chứ không `throw`

Quyết định kiến trúc, không phải lười. Trong stream tần suất cao, một frame hỏng là **chuyện bình thường**,
không phải sự kiện ngoại lệ. Dùng exception cho chuyện bình thường thì:

- caller phải bọc `try/catch` quanh **mỗi** frame
- quên một chỗ = chết process
- exception có chi phí (capture stack trace)

`null` đưa "frame này bỏ qua" vào **type system**: `PriceTick | null` buộc caller phải xử lý —
`if (tick)` không thể quên được, compiler bắt.

### Hai tầng validation, hai triết lý ngược nhau

| | `env.ts` (Zod) | `binanceMessage.ts` (guard tay) |
|---|---|---|
| Tần suất | 1 lần lúc boot | ~50 lần/giây |
| Sai thì | **Crash ngay** | **Bỏ qua, chạy tiếp** |
| Lý do | Sai config = mọi thứ vô nghĩa | Sai 1 frame = mất 1 tick |
| Chi phí | Không quan trọng | Quan trọng |

Đây là **fail-fast vs fail-soft**. Cùng một codebase mà hai nơi xử lý lỗi ngược nhau — hoàn toàn có chủ đích.
Chọn đúng theo ngữ cảnh mới là kỹ năng.

`loadEnv()` còn thể hiện một nguyên tắc nữa: `safeParse` + `flatten()` để gom **tất cả** lỗi vào một Error.
Sai 3 biến thì báo cả 3, không bắt người dùng sửa-chạy-sửa-chạy 3 vòng.

## 5. Số trong JavaScript — chỗ tiền bạc dễ sai nhất

### Vì sao Binance gửi `p` là string

Vì `JSON.parse` của mọi ngôn ngữ sẽ ép số về float của ngôn ngữ đó và **mất chính xác không thể lấy lại**.
Gửi string là cách sàn bảo toàn giá trị chính xác và đẩy trách nhiệm parse cho client.
Đây là chuẩn chung của mọi API tài chính.

### `parseFloat` vs `Number` — khác thật

```js
parseFloat("")             // NaN      ← muốn thế
Number("")                 // 0        ← THẢM HỌA: giá 0 kích hoạt mọi alert
parseFloat("92145.30abc")  // 92145.3  ← dễ dãi với rác phía sau
Number("92145.30abc")      // NaN      ← nghiêm khắc
parseFloat(null)           // NaN
Number(null)               // 0        ← lại là 0
```

Với dữ liệu tài chính, `Number("")` trả `0` là lỗi chết người. `Number.parseFloat` là lựa chọn đúng.

### `Number.isFinite` vs `isFinite` toàn cục

```js
isFinite("")               // TRUE  ← ép "" → 0 → hữu hạn!
Number.isFinite("")        // false ← không ép kiểu, đúng ý
Number.isFinite(NaN)       // false
Number.isFinite(Infinity)  // false
```

Bản toàn cục **ép kiểu trước khi kiểm tra**, gần như luôn sai ý bạn. Parser dùng `Number.isFinite` — chuẩn.

### IEEE-754 — cái bẫy chờ ở M3

Mọi `number` trong JS là double 64-bit. `0.1 + 0.2 === 0.3` là `false`.

M1 chỉ log ra nên không sao. M3 so sánh cắt ngưỡng thì cần biết:
`92145.30` không biểu diễn chính xác được ở nhị phân. Phép `>=` vẫn **nhất quán** vì cả giá lẫn ngưỡng
đều qua cùng đường parse, và ngưỡng thực tế (90000, 3000) đủ thô để không bị ảnh hưởng.

**Nhưng** hệ thống giao dịch thật không dùng float — họ dùng số nguyên đã scale (satoshi) hoặc thư viện decimal.
Biết giới hạn của công cụ mình dùng là một phần của việc học.

### `T` vs `E`

Trong payload `@trade`: `T` = trade time, `E` = event time (cả hai Unix ms).
Parser dùng `T` — đúng, vì ta muốn thời điểm **giao dịch xảy ra**, không phải thời điểm Binance đóng gói tin.

## 6. TypeScript: hai kỹ thuật đáng học

### Declaration merging — làm EventEmitter type-safe

`EventEmitter` gốc khai báo `on(event: string | symbol, listener: (...args: any[]) => void)`.
Tức là `on("tikc", …)` (gõ sai) vẫn compile, và `tick` trong callback là `any`.

`binancePriceService.ts` khai báo một `interface` **trùng tên** với `class`.
TypeScript **gộp** chúng lại, và overload hẹp hơn được ưu tiên:

```ts
priceService.on("tick", (tick) => …);   // tick tự suy ra PriceTick ✓
priceService.on("tikc", …);             // lỗi compile ✓
```

Đây là kỹ thuật chuẩn để type hoá EventEmitter trong TS.
Node 20+ còn có lựa chọn thay thế là generic `EventEmitter<T>`, nhưng declaration merging phổ biến hơn
và hoạt động với mọi phiên bản.

### `ReadonlySet` — kiểu đóng vai trò hợp đồng

`parseTradeMessage` nhận `ReadonlySet<string>` chứ không phải `Set<string>`.
Runtime vẫn là `Set` bình thường — nhưng compiler **chặn `.add()` / `.delete()`** bên trong hàm.

Chữ ký hàm tự nói: _"tôi chỉ đọc, tôi không đụng vào set của bạn"_. Kiểu là tài liệu, không chỉ là kiểm tra.

> **`Set` hay `Array` cho `tracked`?** Với 2 phần tử, O(1) vs O(n) chênh nhau bằng không —
> nói "`Set` nhanh hơn" ở đây là ngụy biện. Lý do thật là **ngữ nghĩa**: đây là tập hợp không trùng lặp,
> không phải danh sách có thứ tự. Chọn cấu trúc dữ liệu theo ý nghĩa trước, hiệu năng sau.

## 7. Hai lỗ hổng thật đang nằm trong code M1

Không phải bài tập — quan sát thật, để thấy kiến thức trên dùng vào đâu.

### `process.exit()` giết luôn cả close handshake

```ts
const shutdown = (signal) => {
    priceService.stop(); // gửi close frame — BẤT ĐỒNG BỘ
    process.exit(0);     // giết process NGAY LẬP TỨC
};
```

`socket.close()` khởi động **closing handshake**: gửi close frame, chờ server trả lời.
`process.exit()` không chờ gì cả — kết thúc process ngay, không xả buffer chưa ghi, không chạy nốt callback nào.

Nên close frame gần như chắc chắn không bao giờ rời khỏi máy. Binance thấy kết nối đứt đột ngột
thay vì được đóng lịch sự. M1 vô hại (đã ghi rõ là skeleton), nhưng cách đúng ở M6 là:
dừng nhận cái mới → chờ handle tự đóng (có timeout cứng) → để process thoát **tự nhiên** vì hết handle —
đúng theo nguyên lý ở [mục 1](#1-vòng-đời-process--event-loop).

### Logger đang ghi đồng bộ (trên macOS + terminal)

Node xử lý `process.stdout` khác các stream khác, và **phụ thuộc nền tảng lẫn đích ghi**:

| stdout nối tới | macOS/POSIX |
|---|---|
| TTY (terminal) | **đồng bộ** |
| Pipe | bất đồng bộ |
| File | đồng bộ |

`npm run dev` trong terminal ⇒ TTY ⇒ **mỗi `logger.info(tick)` là một lần ghi chặn event loop**.
Ở tốc độ M1 thì không đáng kể, nhưng nó nghĩa là bạn đang có sẵn một điểm block trên hot path
ngay cả khi chưa thêm gì. Thử `npm run dev | cat` để đẩy stdout qua pipe và so sánh.

Đây cũng là lý do pino có transport chạy ở worker thread riêng — chủ đề của các milestone sau.

## 9. Dẫn sang M2

| Kiến thức M1 | Trở thành yêu cầu nào ở M2 |
|---|---|
| Handle mất ⇒ process thoát lặng lẽ ([§1](#1-vòng-đời-process--event-loop)) | Phải reconnect, nếu không rớt mạng = chết im |
| Listener throw ⇒ `uncaughtException` ([§3](#hệ-quả-3--listener-throw-sẽ-giết-process)) | Bắt `uncaughtException` / `unhandledRejection` |
| Listener không được gỡ khi `stop()` ([§3](#bẫy-đang-chờ-ở-m2)) | `removeAllListeners()` trước mỗi lần reconnect |
| `setTimeout` chỉ chính xác khi loop rảnh ([§1](#thí-nghiệm-3--thứ-tự-thực-thi)) | Test backoff bằng **fake timers**, không bằng `sleep` thật |
