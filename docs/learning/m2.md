## 1. Vấn đề: M1 chết im như thế nào

Cho `fakeBinanceServer` bơm tick 8 giây rồi cắt TCP. App là code M1 nguyên trạng.

```
t+0ms      server cắt kết nối (TCP FIN)
t+4ms      handler close chạy → 1 dòng log level 40
t+99ms     process thoát, exit code 0
```

Kết nối sống 8001ms, nhận 62 tick. Toàn bộ dấu vết còn lại:

```json
{"level":40,"code":1006,"msg":"Binance WS closed (reconnect arrives in M2)"}
```

Điểm nguy hiểm không phải nó chết, mà là **`exit code 0`**.

Với thế giới bên ngoài, `0` nghĩa là *"hoàn thành bình thường"*. systemd `Restart=on-failure`,
Docker `restart: on-failure`, PM2 — đều **không** khởi động lại, vì theo chúng chẳng có failure nào.

> Chết im với exit 0 **tệ hơn crash**. Crash thì còn có người cứu.

## 2. Phát hiện quyết định thiết kế: `error` không đáng tin

Chạy 4 kịch bản đứt kết nối khác nhau, xem `ws` bắn event nào:

| Kiểu đứt | `error`? | close code | exit |
|---|---|---|---|
| `close` — WS close frame (server bảo trì, mốc 24h) | không | 1001 | 0 |
| `terminate` — TCP FIN (rớt mạng êm) | không | 1006 | 0 |
| `reset` — TCP RST (đứt cáp) | không | 1006 | 0 |
| **không có server** — ECONNREFUSED | **có** | 1006 | 0 |

> **`close` LUÔN bắn. `error` chỉ bắn khi bắt tay thất bại — không bao giờ khi đang chạy mà mất kết nối.**

Với `ws`, một khi kết nối đã thiết lập thì cái chết của mạng — FIN hay RST đều vậy — được báo qua
`close`, không qua `error`. `error` dành cho lỗi handshake (bị từ chối, DNS hỏng) và vi phạm giao thức.

### Hệ quả

Đặt logic reconnect vào `error` — rất tự nhiên vì "mất mạng là lỗi mà" — sẽ cho ra một con bot
**không bao giờ tự nối lại khi rớt mạng**, và chỉ nối lại đúng lúc không cần.

```
Reconnect drive từ "close".
"error" chỉ để log — nhưng vẫn BẮT BUỘC có listener, vì emit("error")
không listener sẽ throw (xem m1.md §3).
```

`PLAN.md` viết *"tự reconnect khi `close`/`error`"*. Số đo cho thấy `close` là đủ và đúng;
thêm `error` vào chỉ tạo ra reconnect kép cho cùng một lần đứt.

## 3. Bài học phụ: nghi ngờ dụng cụ đo trước

Lần chạy đầu cho `exit=137`, 298 tick, không có sự kiện drop nào — số liệu vô nghĩa. Nguyên nhân:

- Server smoke-test **vẫn sống** → giữ cổng → server thí nghiệm chết vì `EADDRINUSE`,
  app nói chuyện với server cũ (loại không drop)
- `npx tsx` **spawn tiến trình con** → `kill` vào cha để lại cháu mồ côi vẫn ghi log

Sửa: chạy `node --import tsx` (một process duy nhất), và rig **tự kiểm tra server đã lên**
trước khi bắt đầu đo.

> Khi số liệu trông kỳ lạ, nghi ngờ dụng cụ đo trước khi nghi ngờ hệ thống.

## 4. Nghiệm thu: chạy lại chính thí nghiệm đó

Server cắt mỗi 4s trong 14s, rồi **giết hẳn** server trong 22s:

```
Pha A — server còn sống, cắt mỗi 4s
   10ms  ✓ CONNECTED
 4014ms  ✗ closed 1006  attempt=1 →   950ms
 4971ms  ✓ CONNECTED
 8973ms  ✗ closed 1006  attempt=1 →   958ms     ← attempt RESET nhờ open thành công
 9935ms  ✓ CONNECTED
13886ms  ✗ closed 1006  attempt=1 →   850ms

Pha B — server bị giết
14739ms  ! ECONNREFUSED → attempt=2 →  1899ms
16642ms  ! ECONNREFUSED → attempt=3 →  3722ms
20368ms  ! ECONNREFUSED → attempt=4 →  6856ms
27227ms  ! ECONNREFUSED → attempt=5 → 15933ms

app vẫn sống sau 36s ✓   ·   90 tick nhận được qua 3 phiên kết nối
```

Đọc được ba điều từ đây:

1. **Reset hoạt động** — pha A `attempt` luôn là 1, vì mỗi lần `open` thành công đều xoá bộ đếm
2. **Tăng lũy tiến hoạt động** — pha B: 1899 → 3722 → 6856 → 15933, nhân đôi có jitter, trần 30s
3. **Cả hai đường lỗi đều được phủ** — pha B có `error` trước `close`, reconnect vẫn chạy vì nó drive từ `close`

## 5. Cách tự chạy lại

```bash
# Binance giả, cắt kết nối sau 8s
FAKE_PORT=8081 DROP_AFTER_MS=8000 DROP_MODE=terminate \
  node --import tsx test/harness/fakeBinanceServer.ts &

BINANCE_WS_URL=ws://localhost:8081 node --import tsx src/index.ts
```

| Env | Ý nghĩa | Mặc định |
|---|---|---|
| `FAKE_PORT` | cổng lắng nghe | 8081 |
| `TICK_MS` | nhịp gửi frame | 250 |
| `DROP_AFTER_MS` | cắt sau bao lâu; 0 = không cắt | 0 |
| `DROP_MODE` | `close` \| `terminate` \| `reset` | terminate |

Dùng `node --import tsx`, **không** dùng `npx tsx` — `npx` sinh tiến trình con làm sai phép đo.

## 6. Quyết định đáng bàn: `uncaughtException` nên thoát hay sống tiếp?

`PLAN.md` viết *"bắt `unhandledRejection` / `uncaughtException` để log, không crash âm thầm"* — không nói rõ có thoát hay không. Cách hiện tại:

| Sự kiện | Xử lý | Vì sao |
|---|---|---|
| `unhandledRejection` | log `error`, **chạy tiếp** | Một promise reject hiếm khi làm hỏng state |
| `uncaughtException` | log `fatal`, **`exit(1)`** | State không còn tin được; mã khác 0 để supervisor restart |

Chọn `exit(1)` chính là áp dụng bài học ở §1: chết ồn ào thì được cứu, chết im thì không.
Muốn "không bao giờ thoát" đúng nghĩa đen thì bỏ dòng `process.exit(1)` trong
[`src/index.ts`](../../src/index.ts) — nhưng khi đó process sẽ chạy tiếp với state có thể đã hỏng.

## 7. Tắt êm (graceful shutdown)

Lỗ hổng phát hiện ở [m1.md §7](./m1.md#7-hai-lỗ-hổng-thật-đang-nằm-trong-code-m1): `stop()` gửi close frame
(bất đồng bộ) rồi `process.exit(0)` giết process ngay — close frame không kịp rời máy.

Cách sửa, đúng theo nguyên lý "process sống nhờ handle":

```
SIGTERM
  ├─ đặt chốt timeout 5s  → hết giờ thì exit(1)
  ├─ await priceService.stop()      ← chờ socket đóng THẬT
  │     ├─ stopped = true, clear cả 2 timer
  │     ├─ once(socket, "close")    ← promise chờ sự kiện
  │     └─ socket.close(1000, "shutting down")
  ├─ clearTimeout(chốt)
  └─ log "Shutdown complete"   → KHÔNG gọi exit(); hết handle, Node tự thoát
```

Đo được cả ba nhánh:

| Kịch bản | Server thấy | exit | Thời gian |
|---|---|---|---|
| SIGTERM bình thường | `code=1000 reason="shutting down"` | **0** | 49 ms |
| Đối tác treo (server bị `SIGSTOP`) | — | **1** | 5001 ms |
| SIGTERM lần hai lúc đang tắt | — | **1** | 1092 ms |

Dòng `code=1000, reason="shutting down"` ở log server là bằng chứng không thể giả: chỉ xuất hiện khi
close frame thật sự đi tới nơi. Trước khi sửa, server sẽ thấy `1006` (đứt bất thường, không có close frame).

Ba chi tiết đáng chú ý:

- **Timeout thoát `exit(1)`, không phải `0`** — cùng lý do ở §1: tắt không sạch phải ồn ào để supervisor biết.
- **Không `unref()` cái chốt timeout** — nó cần giữ process sống đủ lâu để tự bắn nếu shutdown treo.
- **`once()` reject nếu `error` đến trước `close`** — lỗi lúc đang đóng vẫn coi là đóng xong, nên phải `.catch()`.
